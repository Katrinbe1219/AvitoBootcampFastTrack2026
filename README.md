# Avito Bot Detection

Классическая ML-задача: по логам поведения (события за 24-часовое окно) определить,
является ли `cookie_id` ботом. Метрика — precision при recall ≥ 0.70 (`metric.py`).
Никаких LLM/внешних API, никаких хардкодов по id — только признаки из сырых событий и
одна классическая модель.

## Файлы
- analyse.ipynb: в нем происходит анализ признаков, их связь, составляет таблица признаков,
которая сохраняется в train_features.pkl, test_features.pkl

- tests.ipynb: обучение модели и получение файла submission.csv

## Baseline

Точка отсчёта — константа (`target.mean()`): без единого признака и без обучения, просто
средняя доля ботов. Любая модель дальше сравнивается именно с этим честным "полом", а не с нулём.

## Отбор признаков и Information Value

Кандидаты признаков (тайминги между событиями, курсор, доли типов событий,
диверсификация по товарам/категориям и т.д.) сначала проверялись через **Information
Value (IV)**. Важная оговорка: IV — это заведомо субъективный, предварительный фильтр —
он оценивает признак **в изоляции**, не учитывая ни его взаимодействие с остальными
признаками, ни то, как его использует сама модель. Высокий IV не гарантирует пользы в
комбинации, низкий — не гарантирует бесполезности; окончательное решение принималось
только по факту прироста метрики на модели.

## Очистка исходных данных

Сырые данные содержали неочевидные искажения, которые нужно было заметить и поправить
до построения признаков:
- `platform` приходил с дублирующимися по смыслу значениями разного регистра/написания
  (например, `iphone` нужно было привести к `ios`) — без нормализации один и тот же
  реальный класс платформы считался бы за несколько разных.
- `eid` и `event_name` — избыточные кодировки одного и того же набора из 9 типов событий;
  использовался только `event_name`, `eid` не нужен.

## User-Agent: библиотеки-источники трафика

Строка `user_agent` разбиралась через регулярные выражения, чтобы отделить три разных
класса: настоящие браузеры (`^Mozilla/`), родное приложение Avito (`^Avito/`) и всё
остальное — сторонние HTTP-библиотеки/скрипты (`curl`, `python-requests`, `scrapy` и
т.п.), которые реальные люди в норме не используют для похода на сайт.

## Пропуски и NaN

Часть пропусков в данных структурна, а не случайна — например, `pointer_x`/`pointer_y`
всегда пустые или заполненные **вместе** (то же для `search_query`/`search_page`), это
свойство платформы/типа события, а не потеря данных. 
Отдельная проблема — признаки, которым для вычисления нужен минимум наблюдений (например, `std`/`mean` гэпов между событиями требуют 
хотя бы 2 события у куки): такие NaN нельзя просто занулить, потому
что "не хватило данных" и "настоящий ноль" — разные вещи, которые модель должна уметь
различать. Использовался приём с sentinel-значением: пропуски помечались как `-1`, а
границы бинов при анализе IV расширялись отдельным значением ниже `-1`, чтобы такие
куки не терялись при группировке и не путались с реальными нулями.

## Энтропия распределения событий

Для признака `events_entropy` использована энтропия Шеннона по распределению типов
событий (`event_name`) внутри окна одной куки: низкая энтропия — активность
сконцентрирована на одном-двух типах действий (характерно для скриптового,
однообразного поведения), высокая — куки ведёт себя разнообразно, как обычно делает
живой человек, чередуя просмотры, поиск, избранное и т.д. В отличие от доли одного
конкретного типа события, энтропия — это одно число, обобщающее сразу всю структуру
смеси всех типов событий.

## Утечка данных

По ходу работы нашлась реальная ловушка: часть событий в `events.csv.gz` выходит за
пределы заявленного окна наблюдения куки. В частности, `captcha_shown` 
встречается **только после** окончания окна.
Все признаки пересобраны на строго отфильтрованных по `window_start_ts`/`window_end_ts`
событиях.

## Модель

Единая модель на всех этапах — **LightGBM** (градиентный бустинг): нативно работает с
пропусками (не нужно их заполнять искусственно), не требует нормализации признаков,
устойчив к выбросам в count-based фичах, которых в этой задаче большинство.

## Методология проверки признаков

- Сначала признаки добавлялись **по одному** поверх текущей лучшей комбинации — наглядно
  показывает предельный вклад каждого, но на маленькой выборке (~900 ботов) это шумно:
  слабый сам по себе, но полезный в комбинации признак легко "проигрывает" случайно и
  отбрасывается навсегда.
- Дальше перешли на проверку **группами** (по смысловым веткам — тайминги, доли событий,
  диверсификация и т.д.): группа принимается только если даёт прирост целиком, что
  устойчивее к шуму отдельных слабых признаков внутри неё.

## Методология валидации

- Изначально — один cutoff по времени (`window_start_ts`), аналогично `quickstart.ipynb`.
- Позже — расширение до **нескольких соседних cutoff'ов**, чтобы оценивать не единичное
  число, а среднее и разброс: единичный сплит может случайно оказаться удачным или
  неудачным, а среднее по нескольким — куда честнее отражает, чего ждать от модели на
  реальном будущем.

## Наиболее влиятельные признаки

Топ-10 признаков финальной модели по `feature_importances_` (LightGBM, суммарный gain по
числу разбиений):

1. `median_gap` — медиана паузы между событиями
2. `s_page_mean` — средняя глубина пагинации поиска
3. `item_location_count` — число разных локаций просмотренных объявлений
4. `events_entropy` — энтропия распределения типов событий
5. `variation` — коэффициент вариации паузы (std/mean)
6. `std_gap` — стандартное отклонение паузы
7. `pointer_x_std` — разброс координаты курсора по X
8. `mean_gap` — средняя пауза между событиями
9. `seller_page_view_share` — доля просмотров страницы продавца
10. `item_category_count` — число разных категорий просмотренных объявлений


## Результат

Baseline (константа) → первая модель → финальный набор признаков: рост с ~0.09 до
**0.69** на реальном test.
